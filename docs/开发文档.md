# Nako 开发文档

> 本文档基于对 Nako 代码库的实际结构分析，核对《开发设计文档.md》中约定的插件化设计，并说明如何按现有架构进行开发。
>
> 代码库按《开发设计文档.md》的 12 模块组织，插件契约和主要依赖边界由运行时与架构脚本校验，旧 `src/`、`server/` 兼容目录已不存在。五项接口收敛已落实到公共类型、运行校验和回归测试；具体清理范围与保留理由见《插件契约收敛与旧代码清理.md》。这不代表脚本能证明任意实现都符合全部设计约束。

---

## 1. 项目概览

- 定位：Nako 单机插件画布（`package.json` name `nako-canvas`，version `1.0.0`，`"type": "module"`）。
- 运行形态：Electron 桌面壳（`apps/desktop`）+ 本地 Express 后端（`apps/backend`）+ 浏览器画布（`apps/canvas`）。
- 核心机制：**进程内、可信代码的插件宿主**（不是 JS 沙箱），插件通过 manifest 声明能力、服务和凭据，由 `kernel` 统一加载、激活、卸载。
- 关键脚本（`package.json`）：
  - `npm run check` = 架构校验 + 本地化红线 + 类型检查 + 单测 + 画布/启动器构建 + 后端冒烟（正常/禁用 Agent 两种）。
  - `npm run check:architecture` 单独跑依赖方向校验。
  - `npm run build:model-catalog` 聚合各 Provider 的 `models.ts` 生成模型目录。

## 2. 代码结构

### 2.1 顶层目录

| 目录 | 作用 |
| --- | --- |
| `modules/` | 12 个业务/基础模块（对应设计文档的 12 个功能模块） |
| `plugins/` | 适配器插件：Provider、工作流执行器、存储、媒体、平台 |
| `apps/` | 三个宿主入口：`backend`、`canvas`、`desktop` |
| `config/` | 6 个装配目录（插件注册清单） |
| `contracts/` | （不存在，稳定契约统一在 `modules/contracts/`） |
| `scripts/` | 构建、架构校验、冒烟、发布等工具脚本 |
| `tests/` | 单元/集成/冒烟测试 |
| `integrations/comfyui/` | ComfyUI 节点扩展（外部集成，非插件） |
| `docs/` | 设计、开发、更新、验证等文档 |

旧 `src/`、`server/` 目录已删除；`check-architecture.mjs` 会在它们再次出现时报错。

每个模块遵循统一的公开边界约定：

- `api/`：跨模块公开的纯函数、类型、组件，必须同步列入 `exports.json`。
- `index.js` / `browser.ts` / `rootPlugin.tsx` / `serverPlugin.js` / `desktopPlugin.mjs` / `registryPlugin.js`：模块入口，允许被跨模块导入。
- 其余文件为私有实现，禁止跨模块引用（由架构脚本强制）。

### 2.3 插件适配器 `plugins/`

`plugins/` 下按设计文档的“具体实现通过插件注入”组织为 5 类、共 24 个插件：

| 类型 | 目录 | 插件 | 说明 |
| --- | --- | --- | --- |
| provider | `plugins/providers/` | 14 个：`openai`、`doubao`、`kling`、`runninghub`、`mureka`、`dreamina`、`jimeng`、`aliyun`、`grok`、`deepseek`、`official-text`、`libtv`、`seedvr2`、`ecloud` | 设计文档列出的 6 家（openai/doubao/kling/runninghub/mureka/dreamina）全部在列，另有 8 家扩展 |
| workflow | `plugins/workflows/` | `local-comfyui`、`runninghub-workflow`、`runninghub-webapp` | 对应设计文档的 `LocalComfyExecutor`、`RunningHubWorkflowExecutor`、`RunningHubWebAppExecutor` |
| storage | `plugins/storage/` | `sqlite`、`task-journal`、`agent-files` | SQLite 是 `ProjectRepository` 的一种实现 |
| media | `plugins/media/` | `filesystem`、`ffmpeg-sharp` | 文件系统媒体库 + FFmpeg/sharp 处理 |
| platform | `plugins/platform/` | `text-transport` | 文本模型传输 |

### 2.4 装配目录 `config/`

插件通过 6 个清单装配，路径相对于清单文件本身：

| 文件 | 内容 | 条目数 |
| --- | --- | --- |
| `backend-plugins.json` | 核心注册表 + 全部适配器（Provider、执行器、存储、媒体、平台） | 26 |
| `application-plugins.json` | 后端业务应用模块（HTTP 路由贡献） | 8 |
| `browser-plugins.json` | 浏览器 UI 插件（相对 `apps/canvas`） | 11 |
| `desktop-plugins.json` | 桌面工作区插件 | 1 |
| `model-plugins.json` | 模型定义贡献（`models.ts` 导出列表） | 12 |
| `plugins.json` | `disabled` 禁用清单 + `options` 运行配置 | — |

清单条目字段：

- `id` + `entry` + `manifest`：通用；实现中的 `manifest` 必须与清单 `manifest` 完全匹配（`lazyPlugin.js` 校验）。
- `factory` + `options`：后端工厂插件（如 `storage.sqlite` 的 `createSqlitePlugin`）；`options` 值映射宿主注入的路径名（`libraryDirectory`、`privateDirectory`、`generationDirectory`）。
- `credentialKeys`：该插件被授权的密钥名（供 `credentialStore` 装配）。
- `credentialGrants`：该插件可读取的凭据命名空间。
- `configPrefixes`：允许该插件通过 `context.config.get()` 读取的环境变量前缀（密钥类除外）。
- `disabled`：只注册元数据、不激活实现；被依赖的必需插件被禁用时，宿主明确拒绝启动。

### 2.5 宿主入口 `apps/`

| 目录 | 关键文件 | 作用 |
| --- | --- | --- |
| `apps/backend/main.mjs` | 后端启动 | 装配 `createServerPluginHost`，先挂认证边界再挂路由，按 phase 10/20/30 挂载贡献路由，`/api/plugins` 暴露插件状态 |
| `apps/canvas/` | `bootstrap.ts`、`main.tsx` | 浏览器侧按 `browser-plugins.json` 激活 UI 模块 |
| `apps/desktop/src/` | `main.mjs`、`windowManager.mjs`、`backendSupervisor.mjs`、`pluginHost.mjs`、`preload.cjs` | Electron 主进程：窗口、IPC、后端进程管理、桌面插件宿主 |
| `apps/desktop/launcher/` | 启动器 | 独立启动/状态页 |

## 3. 插件化运行时

### 3.1 稳定契约 `modules/contracts/`

- `PLUGIN_API_VERSION = '1.0.0'`，宿主按范围（精确、`^x.y.z`、`>=x.y.z`）校验兼容性（`kernel/index.js` 的 `satisfiesVersion`）。
- `PLUGIN_TYPES = ['module', 'provider', 'workflow', 'storage', 'media', 'platform']`。
- `SERVICES` 常量定义核心服务名（`generation.providers`、`project.repository`、`media.store`、`media.processor`、`generation.service`、`workflow.service`、`identity.credentials`、`local.runtime`）；诊断服务已移除。
- `ERRORS` 定义统一错误码（`PLUGIN_INVALID_MANIFEST`、`PLUGIN_API_INCOMPATIBLE`、`PLUGIN_DEPENDENCY`、`PLUGIN_PERMISSION_DENIED`、`PLUGIN_BUSY` 等）。
- `index.d.ts` 定义稳定类型：`PluginManifest`、`PluginContext`、`NakoPlugin`、`MediaStore`、`MediaProcessor`、`ProjectRepository`、`GenerationProvider`、`GenerationKind`、`WorkflowExecutor` 等。
- `contracts` 不依赖任何业务模块（架构脚本强制：`modules/contracts/` 只能 import `modules/contracts/` 内的文件）。

### 3.2 宿主 `modules/kernel/`

`PluginHost`（`modules/kernel/index.js`）是插件系统核心：

- **注册/加载**：`register()` 使用 contracts 校验 id、版本范围、类型、依赖、服务声明、凭据/配置白名单、布尔卸载标记及 Provider descriptor；拒绝重复声明和无效生命周期方法。`load()` 串行激活，`start()` 按依赖拓扑加载。
- **依赖解析**：`dependencies` 声明依赖插件，检测循环依赖和缺失依赖，校验版本范围。
- **服务注册表** `ServiceRegistry`：`register/get/optional/has/list/removeOwner`，重复注册报错，卸载时按 owner 清理。
- **能力访问控制**：插件只能读取 manifest 中 `services.requires/optional/provides` 声明的服务，未声明访问抛 `PLUGIN_PERMISSION_DENIED`。
- **事件总线** `EventBus`：`on/emit`，监听器异常走宿主 `logger.error`，不影响主流程。
- **凭据访问控制**：`context.credentials.get(providerId)` 要求 manifest `credentials` 包含该命名空间，且宿主 `credentialGrants[id]` 也包含，否则拒绝。
- **生命周期**：`registered → activating → active → (unload) → registered`，激活失败回滚清理并标记 `failed`。
- **卸载**：有活动依赖者拒绝卸载；`reloadRequired === true` 或 `canDeactivate() === false` 时拒绝热卸载（说明为“需重启”）。
- **能力发现**：`discover(capability)` 返回声明该能力且已激活的插件。
- **日志脱敏**：`context.logger` 自动脱敏 `Bearer / sk-` 等密钥模式。

`lazyPlugin.js` 延迟导入实现：激活时才 `import()`，并校验实现内嵌 manifest 与清单 manifest 完全一致。

`application.js` 提供：

- `defineApplicationPlugin({ id, dependencies, requires, provides, optional, activate })`：自动依赖 `host.runtime`、声明 `http.routes`、标记 `reloadRequired: true`。
- `RouteContributions`：有序、可撤销的路由贡献，`phase` 10（严格请求体解析）/ 20（普通 JSON）/ 30（静态文件）分阶段挂载，激活失败或关闭时自动撤销。

### 3.3 插件 Manifest 结构

```ts
interface PluginManifest {
  id: string; version: string; apiVersion: string; type: PluginType;
  dependencies?: Record<string, string>;
  capabilities?: string[];
  services?: { provides?: string[]; requires?: string[]; optional?: string[] };
  credentials?: string[];
  reloadRequired?: boolean;
  contextKeys?: string[];   // 允许透传的运行时上下文键
  configPrefixes?: string[]; // 允许读取的环境变量前缀
  providers?: ProviderDescriptor[];
}
```

最小插件示例（见《插件开发说明.md》）：

```js
export default {
  manifest: {
    id: 'example.echo', version: '1.0.0', apiVersion: '^1.0.0', type: 'module',
    services: { provides: ['example.echo'] },
  },
  activate(context) {
    context.services.register('example.echo', { echo: v => String(v) });
    context.onDispose(() => { /* 释放资源 */ });
  },
};
```

### 3.4 插件类型与 define 助手

| 类型 | 装配方式 | 关键助手 / 工厂 | 注册的服务 |
| --- | --- | --- | --- |
| module（应用/注册表） | `defineApplicationPlugin` 或裸对象 | `modules/kernel/application.js` | `host.runtime`、`http.routes`、业务服务 |
| provider | `defineProviderPlugin(manifest, descriptors, loadHandlers)` | `modules/generation-providers/index.js` | `provider.<Name>` + 向 `generation.providers` 注册 |
| workflow | `defineExecutorPlugin({ id, load, loadClient, exportName, credentialId })` | `modules/workflow-runtime/defineExecutor.js` | `workflow.factory.<id>` + 向 `workflow.executors` 注册 |
| storage / media / platform | `factory` + `options`，工厂返回插件对象 | 各插件 `index.js` | `project.repository`、`media.store`、`agent.persistence` 等 |

`defineProviderPlugin` 关键行为：

- descriptor 必须与 manifest `providers[]` 一致；按 `name` 找实现导出，只发布 `kinds` 声明的生成/恢复方法，不复制内部字段或其他方法；
- `generate*` 方法计数 in-flight 请求，`canDeactivate()` 返回 `inFlight === 0`；
- 每次调用从 `context.credentials.get(manifest.id)` 解析密钥，**绝不信任调用方传入的 provider 配置里的密钥**；
- 每个 kind 必须实现 `generate*`，`canRecover*` 与 `recover*` 必须成对；配置只从宿主读取，调用方配置不能作回退；运行时上下文仅透传固定通道和 manifest `contextKeys`；
- 禁用后调用抛 `PLUGIN_INACTIVE`；再次激活不会恢复旧 context 或旧 handler 的访问权。

`defineExecutorPlugin` 关键行为：

- 通过 `workflow.executors.createClient(id, options)` 向调用方暴露 contracts 中的 12 个白名单方法（只发布实现支持的项），**不暴露内部 store/client/凭据解析器**；
- 执行器方法 `execute/resume/retryInputCleanup/…` 计数活动执行，卸载时校验。

### 3.5 后端宿主装配（`modules/desktop-shell-observability/serverHost.js`）

`createServerPluginHost` 流程：

1. 读 `config/backend-plugins.json`，构建 `credentialStore`（凭据声明）与 `credentialGrants`。
2. `host.register(lazyPlugin(...))` 注册全部后端插件（含工厂）。
3. 注入 `host.runtime` 插件，提供 `host.runtime`、`http.routes`。
4. 注册 `application-plugins.json` 中的业务模块。
5. 校验 `plugins.json` 的禁用项与依赖完整性，`host.start()` 启动。

### 3.6 浏览器与桌面宿主

- 浏览器：`modules/kernel/browser.ts` 的 `browserHost`、`activateBrowserModule`、`trackBrowserResource`。历史 `window.__NAKO_*` 字段名只做类型兼容，运行服务在宿主注册表里，不挂到 `window`。
- 桌面：宿主提供 `desktop.environment`（平台网络、密钥保护、工作区选择、广播、进程启动）；`desktop.identity` 由本地工作区插件提供（无云端认证）。

### 3.7 架构校验 `scripts/check-architecture.mjs`

这是设计文档“关键规则”的**机器化强制**，失败即 `check` 失败：

- 旧 `src/`、`server/` 目录不存在，不得出现 `src/`、`server/` 导入路径。
- 导入必须可解析（相对路径 + 后缀）。
- `modules/contracts/` 只依赖 `contracts`；`modules/kernel/` 只依赖 `kernel` + `contracts`。
- 业务模块不得 import `plugins/` 适配器实现（唯一例外：`modules/generation-core/models/catalog.ts` 聚合 `config/model-plugins.json` 明确登记的 `models.ts`）。构建另校验模型所属 Provider/kind，拒绝夹带实现文件或外部运行依赖。
- `modules/*` 不得 import `apps/`；跨模块只能走 `api/`、入口文件或 `contracts/kernel`。
- `plugins/*` 之间不得 import 其他适配器实现（`/shared/` 共享除外）。
- `ui/` 不得 import `server/` 或 `desktop/`（`ui/desktop/` 桥除外）。
- 禁止 `window.__NAKO_*` 服务定位器和 `app.locals` 未声明服务。
- 5 个目录清单的 id 唯一、entry/manifest 可解析、manifest id 与清单 id 一致。
- `modules/agent/` 不得直接用 `node:fs`（Harness 持久化必须走存储适配器）。
- `modules/asset-media/**/*Router.js` 不得导入 fs、path 或 child_process；素材、素材库、下载路由将存储请求转给 `media.operations`，编辑转给 `media.editing`。

## 4. 与《开发设计文档》的符合性分析

### 4.1 模块映射：12/12 全部落地

《开发设计文档》列出的 12 个功能模块在 `modules/` 下**一一对应存在**，命名一致，职责一致（见 2.2 表）。未出现缺模块、改名或合并。

### 4.2 接口符合性

| 设计文档接口 | 实际落点 | 状态 |
| --- | --- | --- |
| `NakoPlugin { id, version, type, activate, deactivate? }` | `contracts/index.d.ts` 的 `NakoPlugin` + `PluginManifest`；`PluginHost.register` 校验 | ✅（实现更严格：manifest 强制、`canDeactivate?` 补充） |
| `GenerationProvider` | `contracts/index.d.ts` 的 `GenerationProvider`；实际适配层由 `defineProviderPlugin` + manifest `providers[]` 提供 | ✅（见 4.4 差异①） |
| `WorkflowExecutor { canExecute, execute, cancel? }` | `contracts/index.d.ts` 的 `WorkflowExecutor`；实际执行器有 `execute/resume/…` + 独立 client | ✅（见 4.4 差异②） |
| `ProjectRepository { get, save, delete }` | `contracts/index.d.ts` 的 `ProjectRepository`；`storage.sqlite` 提供 `project.repository` | ✅ |
| `MediaStore { save, read, remove }` | `contracts/index.d.ts` 的 `MediaStore`；`media.filesystem` 提供 `media.store` | ✅ |
| `MediaProcessor { crop, trimVideo }` | `contracts/index.d.ts` 的 `MediaProcessor`；`media.ffmpeg-sharp` 提供 `media.processor` | ✅ |

### 4.3 关键规则逐条核对

设计文档《二、目标依赖方向》的落点与现有检查如下；静态检查覆盖导入边界，运行权限依赖使用受控的 PluginContext：

| 设计文档规则 | 实现 / 校验 | 状态 |
| --- | --- | --- |
| `desktop-shell → kernel → contracts` | `apps/desktop` 与 `desktop-shell-observability` 依赖 kernel；kernel 只依赖 contracts（脚本强制） | ✅ |
| 业务模块依赖 kernel 和 contracts | `modules/*` 通过 `api/`、入口文件或 `contracts/kernel` 交叉引用 | ✅ |
| 具体实现通过插件注入 | `generation-provider` → `GenerationProvider`；`workflow` → `WorkflowExecutor`；`storage` → `Repository`；`media` → `MediaStore` | ✅ |
| canvas-ui 不得 import 具体 Provider | `ui/` 不得 import `server/`；业务模块不得 import `plugins/` | ✅ |
| generation-core 不得 import OpenAI/豆包等实现 | Provider 实现都在 `plugins/providers/*`，core 通过 `generation.providers` 按名解析（`requireProvider` 每次调用解析当前激活实现） | ✅ |
| project 不得直接依赖 SQLite 类 | `project` 模块定义 `ProjectRepository` 契约；SQLite 实现隔离在 `plugins/storage/sqlite` | ✅ |
| media 不得在 Router 中直接操作文件系统 | 媒体 Router 的文件操作均移入 `media.filesystem`；处理由 `media.ffmpeg-sharp` 提供，架构脚本禁止 Router 导入文件系统 | ✅ |
| 插件不得访问其他插件内部对象 | 服务访问需声明 + 只暴露有限方法（`Object.freeze` 包装） | ✅ |
| 插件之间通过事件和公共协议通信 | `EventBus` + `contracts` | ✅ |
| 业务模块不得通过 `window.__NAKO_*` / `app.locals` 取核心服务 | 脚本正则强制禁止 | ✅ |
| identity-account 作为安全边界，插件凭据受控 | `credentialStore.get(providerId)` + manifest `credentials` + 宿主 `credentialGrants` | ✅ |
| agent 不直接调 SQLite/Provider/fs | agent 用 `agent.persistence`（存储适配器），Harness 禁 `node:fs` | ✅ |
| local-runtime 平台适配层不被画布直接 import | `ui/` vs `server/` 边界强制 | ✅ |

### 4.4 与设计文档的差异 / 实现细化（均为正向收敛，非违规）

1. **`GenerationProvider` 形状细化**：设计文档的 `generateImage/generateVideo/generateText` 是抽象形状；实际适配层采用“descriptor + handler”，handler 方法为 `generateText/generateImage/generateVideo/generateAudio`，并按 `descriptor.kinds`（`image/video/audio/text`）声明，异步任务增加 `canRecover/recover`。`contracts/index.d.ts` 的 `GenerationProvider` 仍是稳定类型契约。

2. **`WorkflowExecutor` 形状细化**：设计文档的 `execute/cancel` 扩展为 `canExecute/execute/resume/retryInputCleanup/markRecoveryInputsOrphaned/markInputsOrphaned/cleanupInputs`，客户端能力经 `workflow.executors.createClient(id, options)` 的白名单方法暴露（约 15 个，见 `defineExecutor.js`）。

3. **插件对象比设计文档更严格**：设计文档只要求 `id/version/type/activate/deactivate`；实现强制 manifest 校验、`services` 声明式读写控制、凭据授权、`reloadRequired`/`canDeactivate` 热卸载语义。`deactivate` 仍为可选。

4. **模型目录作为“声明式数据贡献”特例**：`config/model-plugins.json` → `build:model-catalog` 生成 `modules/generation-core/models/catalog.ts`，这是架构脚本唯一允许“业务模块 import 插件文件”的场景。

5. **`mediaAssetRouter` 直接操作 fs 的耦合已移除**：现在 `media.filesystem` 提供 `media.store/media.operations/media.agent/media.generation`，`media.ffmpeg-sharp` 提供 `media.processor/media.editing`。

## 6. 开发指南

> 总原则（红线，违反会被 `check:architecture` 拦截）：
> - 不新增旧 `src/`、`server/` 目录；新实现必须归属某个模块或适配器。
> - 跨模块共享的纯函数/组件/类型从所属模块 `api/` 导出并同步 `exports.json`。
> - 有生命周期的服务通过宿主 `context.services.get()` 获取；禁止业务直接 import 适配器实现。
> - 密钥只经 `context.credentials.get(manifest.id)` 获取；禁止业务绕过禁用状态 import Provider 文件。

### 6.1 新增 Provider 插件

1. 建立 `plugins/providers/<name>/`：`manifest.json`、`index.js`、`implementation.js`、`models.ts`。
2. `manifest.json`：`type: "provider"`，声明 `capabilities`（如 `generation.image`）、`services.requires: ["generation.providers"]`、`services.provides: ["provider.XxxProvider"]`、`credentials: ["provider.<name>"]`、`providers: [{ name, kinds, execution, requiredSecrets }]`。
3. `index.js`：`defineProviderPlugin(manifest, manifest.providers, () => import('./implementation.js'))`。
4. `implementation.js`：导出与 `providers[].name` 同名 handler，实现 `generateText/generateImage/generateVideo/generateAudio`，异步任务实现 `canRecover/recover`。
5. 在 `config/backend-plugins.json` 登记 entry、manifest、`credentialKeys`、`credentialGrants`。
6. 模型放 `models.ts`（导出 `TEXT_MODELS/IMAGE_MODELS/VIDEO_MODELS/AUDIO_MODELS`），在 `config/model-plugins.json` 声明导出，然后 `npm run build:model-catalog`。
7. 新增密钥同步 `modules/contracts/providerSecrets.js` 与 `scripts/release/runtimeControl.mjs` 的进程环境允许名单；来源设置、Agent 兼容名单独立显式登记（不能只加模型目录）。

参考：`plugins/providers/openai/`、`plugins/providers/ecloud/`（四类处理器 + 异步恢复 + `referenceUrlParams` 示例见《移动云 MoMA 接入说明》《移动云 Seedance2 接入说明》）。

### 6.2 新增工作流执行器

1. `plugins/workflows/<id>/`：`manifest.json`、`index.js`、`implementation.js`、可选 `client.js`。
2. `index.js` 用 `defineExecutorPlugin({ id, load, loadClient, exportName, credentialId })`。
3. `implementation.js` 实现 `canExecute`（按 `runtime/runtimeKind` 匹配）、`execute`、`resume` 等；`client.js` 实现有限客户端方法。
4. 在 `config/backend-plugins.json` 登记；需要 RunningHub 凭据时加 `credentialGrants: ["provider.runninghub"]`。
5. 错误类与输入校验使用 `contracts/workflowProtocols.js`，不要 import 适配器实现做错误判断。

参考：`plugins/workflows/local-comfyui/`、`plugins/workflows/runninghub-workflow/`、`plugins/workflows/runninghub-webapp/`。

### 6.3 新增存储 / 媒体 / 平台适配器

1. 在 `plugins/storage/`、`plugins/media/`、`plugins/platform/` 建目录，提供 `manifest.json` + `index.js` 工厂函数（如 `createXxxPlugin(options)`）。
2. 工厂返回 `{ manifest, activate }`，在 `activate` 里 `context.services.register('服务ID', 有限对象)` 并用 `context.onDispose()` 释放资源。
3. 在 `config/backend-plugins.json` 登记 `factory` 与 `options`（options 值用宿主路径名 `libraryDirectory`/`privateDirectory`/`generationDirectory`）。
4. 只暴露有限方法，**不要把数据库、密钥或原始客户端对象作为不受限公共服务返回**。

参考：`plugins/storage/sqlite/index.js`、`plugins/media/filesystem/index.js`、`plugins/platform/text-transport/index.js`。

### 6.4 新增后端业务模块

1. 在 `modules/<module>/` 建 `serverPlugin.js`，用 `defineApplicationPlugin({ id, provides, activate })`。
2. `activate` 内创建 `express.Router()`，通过 `context.services.get('http.routes').contribute(context, router, { phase, order })` 贡献路由；不能在模块导入时启动进程或注册路由。
3. 在 `config/application-plugins.json` 登记 entry + `server.manifest.json`。
4. 需要的数据经服务获取（`host.runtime`、`project.repository`、`media.store` 等），不要直接开 SQLite/fs。

参考：`modules/identity-account/serverPlugin.js`。

### 6.5 新增浏览器 UI 模块

1. 在 `modules/<module>/` 建 `browser.ts`（或 `rootPlugin.tsx`），用 `activateBrowserModule(context, activate)` 装配，用 `trackBrowserResource` 登记带 `destroy/dispose` 的对象；安装器返回释放函数时调用 `context.onDispose(fn)`。
2. 在 `config/browser-plugins.json` 登记 entry + `browser.manifest.json`（相对 `apps/canvas`）。
3. 跨模块 UI 能力经宿主服务（`context.services.get('ui.*')`）装配；Agent 在自身 `ui/agent/surfaces.ts` 注册 `ui.agent.surfaces`，画布通过可选插槽渲染。
4. 根视图由 `ui.canvas-shell` 的 `rootPlugin.tsx` 提供 `ui.root`。

### 6.6 新增桌面插件

1. 建 `modules/<module>/desktopPlugin.mjs` + `desktop.manifest.json`。
2. `activate` 内通过 `context.services.get('desktop.environment')` 获取平台环境，注册桌面服务（如 `desktop.identity`）。
3. 在 `config/desktop-plugins.json` 登记。窗口和 IPC 留在宿主，不要在新插件里重复实现。

参考：`modules/identity-account/desktopPlugin.mjs`。

### 6.7 模型目录与聚合

- 每个 Provider 的 `models.ts` 是声明式数据源；`config/model-plugins.json` 声明导出列表。
- `npm run build:model-catalog` 生成 `modules/generation-core/models/catalog.ts` 与后端 `modelCatalog.generated.json`，**不要手改生成文件**。
- 用唯一模型名和 `catalogOrder` 保持排序。

### 6.8 公开 API 边界

- 模块 `api/` 目录是可公开文件；`exports.json` 必须精确列出 `api/` 内每个文件（多列/漏列都会被 `check:architecture` 报错）。
- 跨模块引用只允许：`modules/contracts/*`、`modules/kernel/*`、其他模块的 `api/**`、其他模块的入口文件（`index|browser|rootPlugin|serverPlugin|desktopPlugin|registryPlugin`）、以及 `.json/.css/.svg` 资源。

## 7. 边界与红线

1. **这是可信代码的进程内宿主，不是 JS 安全沙箱**：权限检查阻止的是声明性误用，不能阻止恶意代码自行 import 系统模块。当前不含插件市场、独立发行包或任意第三方代码隔离。
2. **凭据边界**：`identity-account` 是安全边界；第三方插件只能通过受控的 `context.credentials.get(providerId)` 获取自己被授权的密钥，不得读取他人密钥或宿主凭据存储。
3. **本地化红线**：官方服务域名、账号/反馈/更新桥、Relay 与统计上报不得重新进入运行代码（`check:local-only` 强制）。
4. **第三方访问边界**：新增 Provider 只能因用户配置或模型操作访问对应第三方服务；禁止启动时注册官方设备、同步官方账号或上报使用数据；本地诊断可保留，网络上报不可借诊断之名恢复。
5. **热卸载语义**：`reloadRequired: true` 表示通过重启启停，不得据此宣称支持无损热卸载；空闲 Provider 可在进程内启停，有活动请求则拒绝。
6. **不要放宽校验接入**：新插件应补充行为测试，而不是通过放宽 `check` 边界来通过检查。

## 8. 2026-09-18 源码分层与职责拆分

- 运行时凭据存储归属 `identity-account/server/credentials`，Windows DPAPI 桥和 macOS 钥匙串保护器随安全模块维护。发布脚本、桌面宿主和配置路由消费该模块公共 API；旧 `scripts/release` 实现已移除，没有转发兼容文件。
- `/api/config` 由 `module.generation` 贡献，身份模块只管理安全、偏好与外观等自身路由。`config.js` 的环境变量键白名单、编解码和网络值规范化拆入 `server/config/environmentConfig.js`。
- `normalizeLocalComfyServer` 归属 contracts；私有目录保护归属 identity-account；目录授权错误归属 contracts；系统目录选择器归属 local-runtime 平台 API。原 workflow-runtime 内平台实现和旧公共出口已移除。此次检查针对后端模块源码依赖环，不把“插件依赖图无环”当成“源码无环”的替代证据。
- `workflowManager.ts` 仅组织视图、事件与加载；工作流字段、素材、部署、输出、运行观察、库导航分别维护。异步回调共享同一个 session 对象，避免上传模式和轮询令牌变为过期快照。工作流跨模块 DTO/客户端协议归入 contracts 的 workflowEditor/workflowCanvas/workflowClient。
- `canvasApplication.tsx` 仅组合状态、场景、受控操作、保存、导航和副作用 Hook；各视图按职责拆分。Hook 顺序、文档 epoch、自动保存和异步导航校验保留。
- 后端入口拆为 `module.agent`、`module.agent.drama`、`module.agent.storyboard`。Drama 提供 `agent.drama` 服务并拥有规划、执行及草稿工具；Storyboard 拥有 `/api/storyboard`。目前核心 Agent 显式依赖 Drama，停用整组时须同时停用核心和两个子插件；这不是任意热卸载或独立发行包支持。公共服务协议见 `contracts/agentDrama.d.ts`，pi 类型仍在 agent 内部。
- Drama 规划 Router 自带 JSON 解析器，早于 Agent 通用解析器挂载不导致 body 丢失。规划及剧本 JSON 的请求体上限明确为 32 MB；实际 HTTP 测试覆盖有效 JSON、400、413 和路由撤销。

### 自动校验

`check:architecture` 新增禁止 modules → scripts（同时保留 modules → apps）、后端模块源码依赖环检测和源码行数检查。静态导入、转出、字面量动态 import、require、类型 import 均扫描；运行时计算生成的路径不是静态扫描可证明的范围。环错误给出具体文件边。检查已接入 push / pull_request CI，桌面打包 CI 继续执行同一命令。

按《条件约束文档》实施单文件不超过 500 行的检查，原 300 行门槛已修正。优先拆分后的行数：workflowManager 292、canvasApplication 28、workflowManagerClient 265、config Router 183。继续拆分工作流链路后，尚有 51 个历史超长文件（modules 37、plugins 10、scripts/tests 4），见 [源码行数待拆清单](源码行数待拆清单.md)。

### 工作流链路的职责边界

- `contracts/workflowCanvasNodeProtocol.ts` 定义画布工作流节点、输入槽、操作适配器和运行视图作用域。画布和 Agent 直接从 contracts 引用这些类型，协议不依赖业务模块。
- `local-runtime/ui/local/workflowNodeComposition.ts` 只装配节点适配器。结构更新、槽位/几何、参数与素材取值、上传、样例、已验证结果插入、执行观察和回执投影各自维护；共享的是同一个适配器、去重映射和观察器，避免拆分后复制可变状态。
- `workflow-runtime/server/workflowRuntime` 的格式处理拆为 JSON 边界、图结构、artifact 解析、节点 schema、API 分析、UI 连线校验/投影/编译和图比较；参数绑定拆为候选、校验、种子策略、动态素材分支、编译和公开 DTO。原格式/绑定入口仅导出受支持的 API，不暴露所有内部 helper。
- `plugins/workflows/local-comfyui/executor.js` 是插件内部装配根，注入对象保存在私有字段。新执行由预检、暂存、提交、观察、结果本地化和回执发布组成；恢复路径仅读取已持久化元数据并观察原任务，不重新提交。客户端协议、响应限制和错误脱敏独立维护。
- 输入仍在上传前保存确切目标账本；未确认远端停止时保留输入并登记待清理状态。输出回执仍按暂存 → 调度提交证明 → 发布顺序提交；提交前失败回滚，提交后失败交给持久化恢复，不删除已确认输出。
- 原公开入口保留给宿主和模块 API 使用，旧的大型实现已经替换；没有增加旧数据格式转换或备用执行器。当前仍有 51 项行数债务，下一轮可继续拆 `canvasWorkflowGenerator.tsx`、模型声明和 Agent 面板。
