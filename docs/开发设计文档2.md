# 第一部分　模块化设计

> 本部分是模块划分与依赖方向的**基线设计**，每条职责与每个示例接口都已校准到 `modules/` 当前的真实入口与契约形状。
> 相对初版的主要校正如下（初版为抽象示意，本版为实际形状）：
>
> | 位置 | 初版 | 校准后（当前项目） |
> | --- | --- | --- |
> | modules 数量 | 12 个功能模块 | 12 个模块，`modules/` 下命名一一对应（749 个文件，其中 656 个代码文件） |
> | `NakoPlugin` | 扁平 `id/version/type/activate/deactivate?` | 以 `manifest` 为唯一元数据来源，补 `canDeactivate?` |
> | `ProjectRepository` | `get/save/delete` 3 方法 | 4 方法（补 `list()`），`SaveResult = { id, revision }` |
> | `MediaStore` | `read` 返回 `MediaAsset` | `read` 返回 `MediaAsset \| null` |
> | `MediaProcessor` | `crop/trimVideo` 返回 `MediaResult` | 返回 `MediaAsset` |
> | `GenerationProvider` | `id/capabilities()/generateImage?…` | `{ descriptor, handler }`，方法按 `descriptor.kinds` 动态发布 |
> | `WorkflowExecutor` | `execute/cancel?` | 6 方法（`execute/resume/retryInputCleanup/markRecoveryInputsOrphaned/markInputsOrphaned/cleanupInputs`），无 `cancel` |
> | `generation-providers` | 6 家服务商 | **14 个** Provider 插件 |
> | `identity-account` | 含登录登出、Relay 账号 | 云端登录/Relay 已移除，改为**纯本地身份与凭据边界** |
> | `desktop-shell-observability` | 含更新 | 更新桥已移除，保留**本地诊断** |
> | `asset-media` | 「Router 直接操作 fs，需逐步移除」 | 耦合**已完成移除**，Router 层零 fs |
>
> 各模块的深度细节（目录、入口、`exports.json`、服务契约、不变量、扩展点）见**第二部分 第四章**。

## 一、12 个功能模块

### 1. contracts：公共协议与类型

**职责：**

- 节点类型与项目格式：`CanvasNode`、`Project`、`SaveResult`
- 生成请求/结果：`GenerationKind`、`GenerationRequest`、`GenerationResult`、`ModelCapability`
- 工作流格式：`WorkflowDefinition`、`WorkflowRunRequest`、`WorkflowExecutor`、`WorkflowClientMethod`
- 媒体资源格式：`MediaAsset`、`MediaInput`、`MediaStore`、`MediaProcessor` + 操作面契约
- Agent 操作协议：`AgentEvent`（协议 v2）、`CanvasControl`、`AgentSessionSnapshot`、`AgentSessionRepository`
- 插件 Manifest 与上下文：`PluginManifest`、`PluginContext`、`NakoPlugin`
- 错误码和事件定义：`ERRORS`（14 个）、`SERVICES`、`PLUGIN_TYPES`、`PluginError`

**依赖规则：**

- contracts 不依赖任何业务模块：其内部 import 目标必须仍在 `modules/contracts/` 内
- contracts 不允许出现裸包名 import（含 `node:`）
- 这是整个插件系统的稳定 API，优先级最高：`PLUGIN_API_VERSION = '1.0.0'`

**实际入口：** `index.js`（运行时常量 + `PluginError`）、`index.d.ts`（稳定类型）、`pluginValidation.js`（`validatePluginManifest` / `validateProviderDescriptor`）、`workflowProtocols.js`、`canvasControlProtocol.*` 及各域 `*Protocol.js`；共 39 个文件。

### 2. kernel：核心运行时和插件宿主

**职责：**

- 插件注册、加载、卸载，以及依赖拓扑排序（`PluginHost`）
- 插件生命周期状态机：`registered → activating → active | failed`
- 服务注册表（`ServiceRegistry`）：`register/get/optional/has/list/removeOwner`
- 事件总线（`EventBus`）：`on/emit`，监听器异常隔离
- 配置读取：`context.config.get(key, fallback)`
- 日志和错误处理：`context.logger.*` 自动脱敏；统一 `PluginError(code, message)`
- 能力发现：`discover(capability)`
- 版本兼容检查：`satisfiesVersion(version, range)`

**核心接口：**

```ts
interface NakoPlugin {
  manifest: PluginManifest;          // id/version/apiVersion/type/services/credentials/…
  activate(context: PluginContext): Promise<void> | void;
  canDeactivate?(): boolean;         // 热卸载前自检
  deactivate?(): Promise<void> | void;
}
```

`PluginContext` 提供 `pluginId`、`signal`、`services`、`events`、`config`、`credentials`、`logger`、`onDispose`；其中服务读写受 manifest `services.{requires,optional,provides}` 声明约束，越权抛 `PLUGIN_PERMISSION_DENIED`。版本范围支持精确、`^x.y.z`、`>=x.y.z`。

**依赖规则：**

- kernel 只依赖 contracts，不依赖具体 Provider、SQLite 或 ComfyUI
- `modules/kernel/` 的 import 目标只能是 `modules/kernel/` 或 `modules/contracts/`

**实际入口：** `index.js`、`index.d.ts`、`application.js`（`defineApplicationPlugin` / `RouteContributions`）、`lazyPlugin.js`（延迟导入 + manifest 一致性校验）、`browser.ts`（浏览器宿主）；共 6 个文件。

### 3. canvas-ui：画布和界面

**职责：**

- 画布渲染与节点显示
- 拖拽、缩放、选择、连接
- 面板和对话框
- 用户交互状态

**依赖规则：**

- **本模块没有 `server/` 目录**，因此结构上不可能依赖 SQLite / 文件系统 / ComfyUI 客户端
- `ui/**` 不得 import `server/**` 或 `desktop/**`（`ui/desktop/**` 桥接层除外）
- 不得 import 任何 `plugins/**`；跨模块能力只经他模块 `api/**` 或宿主服务取得
- 它只调用 kernel 提供的应用服务和 contracts 定义的数据结构

**启动形态（两段式）：** `browser.ts`（`ui.canvas-ui`，依赖 `ui.asset-media`）安装 11 个稳定适配器；`rootPlugin.tsx`（`ui.canvas-shell`）注册 **`ui.root`** 服务并由 `mount(element)` 渲染根视图；画布另经可选槽位 `ui.agent.surfaces` 渲染 Agent 面板。

**公共 API：** `exports.json` 20 项，位于 `api/ui/{app,canvas,design,dialogs,lifecycle,nodes,settings}`。

### 4. project：项目和工作流文档

**职责：**

- 项目创建、打开、保存、删除
- 文件夹（创建/重命名/删除/移动）
- 版本号（`Project.revision` 乐观并发）
- 冲突合并
- 恢复点
- 项目导入导出
- 工作区路径解析（`api/server/workspace/{workspacePaths,runtimePaths}.js`，被多个模块共同消费）

**仓库接口：**

```ts
interface ProjectRepository {
  get(id: string): Promise<Project | null>;
  list(): Promise<Project[]>;
  save(project: Project): Promise<SaveResult>;   // SaveResult = { id, revision }
  delete(id: string): Promise<void>;
}
```

SQLite 只是该接口的一个实现（`plugins/storage/sqlite` 提供 `project.repository`）。

**依赖规则：**

- 不得 import `sqlite3` 或任何 `plugins/**`
- 文件系统访问一律经 `project.repository` 与 `media.projectFiles`

**服务契约：** 依赖 `storage.sqlite`、`module.asset-media`；requires `project.repository`、`media.projectFiles`；provides `project.snapshots`。

### 5. asset-media：媒体资源与媒体处理

**职责：**

- 图片、视频、音频资源
- 上传、导入、删除
- 缩略图
- 裁剪、拼图、标注
- 音视频帧
- 下载和本地化

**两个接口：**

```ts
interface MediaStore {
  save(input: MediaInput): Promise<MediaAsset>;
  read(id: string): Promise<MediaAsset | null>;
  remove(id: string): Promise<void>;
}

interface MediaProcessor {
  crop(input: CropInput): Promise<MediaAsset>;
  trimVideo(input: TrimInput): Promise<MediaAsset>;
}
```

另有操作面契约补齐 Router 所需批量能力：`MediaLibraryOperations`（11 个操作）、`MediaDownloadOperations`（6 个操作），统一 `(input) => Promise<{ status, body }>`。

**依赖规则：**

- Router **不得** import `fs` / `path` / `child_process`——原 `mediaAssetRouter` 直接操作 fs 和目录结构的耦合**已完成移除**
- 文件系统全部下沉到 `plugins/media/filesystem`（`media.store`/`media.operations`/`media.agent`/`media.generation`），处理下沉到 `plugins/media/ffmpeg-sharp`（`media.processor`/`media.editing`）
- 服务只能返回有限方法集合，不得把目录句柄或客户端对象作为公共服务返回

**服务契约：** requires `media.operations`、`media.editing`；provides `media.projectFiles`。

### 6. generation-core：生成任务核心

**职责：**

- 生成请求标准化
- 任务调度
- 并发控制
- 超时
- 取消
- 任务恢复
- 结果保存
- 计费和授权校验

这个模块只依赖三类抽象：

- `GenerationProvider`（经 `generation.providers` **按名解析当前激活实现**）
- `GenerationTaskStore`（`storage.task-journal` 提供 `generation.taskStore`）
- `GenerationCoordinator`（模块内部组合根）

而不应该直接知道 OpenAI、RunningHub 或 Kling 的具体实现。

**依赖规则：**

- 不得 import 任何 `plugins/providers/**`
- 模型目录聚合（`models/catalog.ts`）是「业务模块 import 插件文件」的**唯一**豁免场景

**服务契约：** 依赖 `module.local-runtime`、`module.identity-account`、`storage.task-journal`、`media.filesystem`；requires `local.runtime`、`generation.taskStore`、`media.generation`、`preferences.repository`；provides `generation.runtime`、`generation.defaults`；另以注册表插件提供 `generation.providers`。

### 7. generation-providers：模型 Provider 插件

这是插件化的重点。每个模型服务商独立为一个插件，当前共 **14 个**：

`openai`、`doubao`、`kling`、`runninghub`、`mureka`、`dreamina`、`jimeng`、`aliyun`、`grok`、`deepseek`、`official-text`、`libtv`、`seedvr2`、`ecloud`（初版列出的 6 家全部在列，另有 8 家扩展）。

**统一契约（descriptor + handler）：**

```ts
interface ProviderDescriptor {
  name: string;                       // 字母数字，≥2 字符
  kinds: GenerationKind[];            // image | video | audio | text
  execution: 'immediate' | 'polling';
  requiredSecrets: string[];
}

interface GenerationHandler {
  id: string;
  capabilities(): ModelCapability[];
  generateImage?(request: GenerationRequest, ctx: ProviderContext): Promise<GenerationResult>;
  generateVideo?(…): Promise<GenerationResult>;
  generateAudio?(…): Promise<GenerationResult>;
  generateText?(…): Promise<GenerationResult>;
  canRecover*?/recover*?;             // 四类 kind 各自成对（polling 任务用）
}

interface GenerationProvider { descriptor: Readonly<ProviderDescriptor>; handler: Readonly<GenerationHandler>; }
```

核心层不再直接 import 具体服务商。插件的 manifest 由 `config/backend-plugins.json` 装配，密钥只经 `context.credentials.get(manifest.id)` 获取。

**实际入口：** `modules/generation-providers/index.js` → `defineProviderPlugin(manifest, descriptors, loadHandlers)`；公共 API 3 项（`BaseProvider`、`materializeInputs`、`providerKit`）。

### 8. workflow-runtime：工作流执行插件

**职责：**

- 工作流定义
- 参数绑定
- 本地 ComfyUI
- RunningHub
- 工作流执行
- 输入输出快照
- 恢复和清理

**执行器契约：**

```ts
interface WorkflowExecutor {
  id: string;
  canExecute(definition: WorkflowDefinition): boolean;
  execute(request: WorkflowRunRequest): Promise<WorkflowRunResult | void>;
  resume?(request: WorkflowResumeRequest): Promise<WorkflowRunResult | void>;
  retryInputCleanup?(runId: string): Promise<unknown>;
  markRecoveryInputsOrphaned?(task: Record<string, unknown>, code: string): Promise<void>;
  markInputsOrphaned?(request: WorkflowInputCleanup): Promise<void>;
  cleanupInputs?(request: WorkflowInputCleanup): Promise<void>;
}
```

（`canExecute` 的实际判据是 `definition.runtimeKind === id`；初版的 `cancel?` 已由上述恢复/清理方法集替代。）

**具体实现（当前 3 个执行器插件）：**

- `workflow.local-comfyui` → `LocalComfyExecutor`
- `workflow.runninghub-workflow` → `RunningHubWorkflowExecutor`
- `workflow.runninghub-webapp` → `RunningHubWebAppExecutor`

它们都是执行器插件，经 `defineExecutorPlugin` 装配；调用方能力经 `workflow.executors.createClient(id, options)` 的 **12 方法白名单**暴露。

**服务契约：** requires `generation.runtime`、`workflow.executors`；provides `workflow.execution`；另以注册表插件提供 `workflow.executors`。错误类与输入校验统一用 `contracts/workflowProtocols.js`。

### 9. agent：Agent、Codex、Drama、Skill

**职责：**

- 对话会话（Harness 运行内核）
- Canvas 操作
- Codex 连接
- Drama 规划
- Skill 管理
- Agent 工具调用
- 分镜与提示词（提示词为独立插件 `module.prompt` / `ui.prompt`）

Agent 不应直接调用 SQLite、Provider 或文件系统，而应该通过以下服务操作画布和项目（初版为抽象名，下列为**实际服务 ID**）：

### 11. identity-account：身份、账号和凭据

**职责（本地优先形态）：**

- 本地用户与本地工作区（无云端账号）
- 用户工作区选择与原子写
- API Key 管理
- DPAPI / 钥匙串加密
- 用户隔离与本地认证边界
- 安全边界支撑：外链策略、脱敏、安全代理、请求上下文

**已移除（不再是本模块职责）：** 登录/登出、注册、Relay 账号、账号类 IPC 桥与官方服务域名回流。这些由本地化红线（`check-local-only.mjs`）强制禁止重新进入运行代码。

这是安全边界，不允许第三方插件直接读取凭据。插件只能通过受控的 `credentialStore.get(providerId)` 获取自己被授权的密钥：

```js
createCredentialStore({ declarations, readSecret })
// 未知命名空间 → CREDENTIAL_SCOPE_DENIED
// 已知命名空间 → 冻结对象，每个 key 为不可枚举 getter，惰性调用 readSecret(key)
```

读取仍需 `manifest.credentials` 与宿主 `credentialGrants` 双重授权，否则抛 `PLUGIN_PERMISSION_DENIED`。

**服务契约：** provides `preferences.repository`（后端）、`desktop.identity`（桌面，消费 `desktop.environment`）。

## 二、目标依赖方向

目标应该是：

```text
desktop-shell
      |
      v
    kernel
      |
      v
  contracts
```

业务模块依赖 kernel 和 contracts：

```text
canvas-ui ------\\
project ---------\\
asset-media ------> kernel -> contracts
generation-core --/
agent ------------/
workflow-runtime /
```

**具体实现通过插件注入：**

| 契约 | 适配器目录 | 提供的服务 |
| --- | --- | --- |
| `GenerationProvider` | `plugins/providers/*`（14 个） | `provider.<Name>` |
| `WorkflowExecutor` | `plugins/workflows/*`（3 个） | `workflow.factory.<id>` |
| Repository | `plugins/storage/*`（3 个） | `project.repository`、`generation.taskStore`、`agent.persistence` |
| `MediaStore` | `plugins/media/*`（2 个） | `media.store`、`media.operations`、`media.processor` |
| 文本传输 | `plugins/platform/text-transport` | `generation.textTransport` |

**关键规则（均由 `scripts/check-architecture.mjs` 机器化强制）：**

- canvas-ui 不得 import 具体 Provider
- generation-core 不得 import OpenAI、豆包等实现
- project 不得直接依赖 SQLite 类
- media 不得直接在 Router 中操作文件系统
- 插件不得直接访问其他插件的内部对象
- 插件之间通过事件和公共协议通信
- 业务模块不得通过 `window.__NAKO_*` 或 `app.locals` 获取核心服务
- `contracts` 只依赖自身；`kernel` 只依赖 `kernel` + `contracts`
- 跨模块引用只能走 `api/**` 或模块入口文件，其余为私有实现
- 旧 `src/`、`server/` 目录与导入路径不得出现

各条规则对应的校验编号与实现落点见**第二部分第七章**。

## 三、总体架构详细设计

### 3.1 分层模型与依赖矩阵

第一部分的依赖方向落到四层，每层的**允许依赖**与**禁止依赖**如下表。这是 `check-architecture.mjs` 的判据来源。

| 层 | 目录 | 允许 import | 明确禁止 |
| --- | --- | --- | --- |
| L0 协议层 | `modules/contracts/` | 仅 `modules/contracts/**`（相对路径） | 任何裸包名、任何其他模块、`node:*` |
| L1 宿主内核 | `modules/kernel/` | `modules/kernel/**`、`modules/contracts/**` | 业务模块、适配器、平台包 |
| L2 业务模块 | `modules/<其余 10 个>/` | `contracts`、`kernel`、他模块 `api/**`、他模块入口文件、`.json/.css/.svg` | `plugins/**`、`apps/**`、他模块私有文件 |
| L3 适配器/宿主 | `plugins/**`、`apps/**` | L2 公共边界 + 同类 `/shared/` | 其他适配器实现（非 shared） |

**依赖矩阵（行 = 依赖方，列 = 被依赖方，✓ 允许 / ✗ 禁止）**

| 依赖方 \ 被依赖方 | contracts | kernel | 其他 modules | plugins | apps |
| --- | --- | --- | --- | --- | --- |
| contracts | ✓ | ✗ | ✗ | ✗ | ✗ |
| kernel | ✓ | ✓ | ✗ | ✗ | ✗ |
| modules/* | ✓ | ✓ | 仅 `api/**` 与入口 | ✗（唯一例外：`generation-core/models/catalog.ts`） | ✗ |
| plugins/* | ✓ | ✓ | 仅公共边界 | 仅 `/shared/` | ✗ |
| apps/* | ✓ | ✓ | 仅公共边界 | 装配期按清单 `import()` | ✗ |

**跨模块「公共边界」定义（精确到路径形态）**：目标文件必须命中以下之一，否则视为 `crosses private module boundary`：

1. `modules/contracts/**`
2. `modules/kernel/**`
3. `modules/<name>/api/**`
4. `modules/<name>/{index,browser,rootPlugin,serverPlugin,desktopPlugin,registryPlugin}.{js,ts,tsx,mjs,cjs,jsx}`
5. 任意模块内的 `.json` / `.css` / `.svg`

### 3.2 插件生命周期状态机

`PluginHost` 强制单一状态机，任何非法迁移都会抛 `PluginError`：

```text
        register()
  [none] ────────► registered ──────────┐
                     │  ▲               │ load()
              load() │  │ unload()      │
                     ▼  │               │
                 activating ───────────┤
                     │  │               │
        activate ok  │  │ activate 抛错 │
                     ▼  ▼               │
                  active    failed ────┘ (reload 只能重新 register)
                     │
             unload(){shutdown:true}
                     ▼
                 registered
```

| 迁移 | 触发 | 校验与副作用 |
| --- | --- | --- |
| `- → registered` | `register(plugin)` | 校验 manifest、`activate` 必须是函数、`deactivate/canDeactivate` 若存在必须是函数、`apiVersion` 兼容、id 不重复；manifest 深拷贝后冻结为元数据 |
| `registered → activating` | `load(id)` | 先递归加载 `dependencies`（检测环 + 版本范围），再创建 `AbortController`、清空 dispose 队列、构造冻结 `PluginContext` |
| `activating → active` | `activate()` 正常返回 | 校验 `services.provides` 中每个服务确实由本插件注册；`events.emit('plugin.activated')` |
| `activating → failed` | `activate()` 抛错 | `#cleanup`：abort signal → 逆序执行 dispose → `services.removeOwner(id)`；`events.emit('plugin.failed')`；错误向上抛 |
| `active → registered` | `unload(id, {shutdown})` | 拒绝条件：存在活动依赖者、`reloadRequired === true`、`canDeactivate() === false`（非 shutdown 时）；然后 `deactivate()` → `#cleanup` |
| 任意 | `start(ids)` 中途失败 | `#stopExcept(已激活集合)`：反复寻找「无活动依赖者」的叶子，逐个 shutdown 卸载（保证逆拓扑序） |

**并发保证**：`register` 同步串行；`load/unload` 全部经 `#serial()` 串入单条 Promise 队列，保证插件启停不会并发交错。

### 3.4 Manifest 校验规则（字段级）

`validatePluginManifest(value)` 逐字段校验，任一失败抛 `PluginError('PLUGIN_INVALID_MANIFEST', 'Invalid plugin contract: <field>')`：

| 字段 | 规则 | 失败字段名 |
| --- | --- | --- |
| `id` | 字符串，`/^[a-z][a-z0-9.-]+$/`（首字母小写，全程小写+数字+`.`+`-`） | `manifest` |
| `version` | 严格 `x.y.z`（`/^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)$/`） | `manifest` |
| `apiVersion` | `x.y.z` 或 `^x.y.z` 或 `>=x.y.z` | `manifest` |
| `type` | ∈ `PLUGIN_TYPES` | `manifest` |
| `dependencies` | 对象；key 为合法 id，value 为版本范围 | `dependencies` |
| `services` | 对象，键只允许 `requires`/`optional`/`provides`；每个值为**非空、去重、无首尾空格**的字符串数组 | `services` |
| `capabilities` / `credentials` / `contextKeys` / `configPrefixes` | 同上（字符串数组、去重、trim） | 同名字段 |
| `reloadRequired` | 布尔（可缺省） | `reloadRequired` |
| `providers` | 仅当 `type === 'provider'`，非空数组；每项经 `validateProviderDescriptor`；`name` 去重；每个 `name` 必须出现在 `services.provides` 中形如 `provider.<name>` | `providers` / `providers.name` / `providers.services` |

`validateProviderDescriptor(value)`：

| 字段 | 规则 |
| --- | --- |
| `name` | 字符串，`/^[A-Za-z][A-Za-z0-9]+$/`（**至少 2 字符**，禁止 `.` 与 `-`） |
| `kinds` | 非空去重数组，取值 ⊆ `GENERATION_KINDS` |
| `execution` | `'immediate'` 或 `'polling'` |
| `requiredSecrets` | 字符串数组（必填），每项 `/^[A-Z][A-Z0-9_]*$/` |

### 3.5 服务注册表与访问控制

`ServiceRegistry`（kernel/index.js）：

- `register(id, value, owner='host')`：id 重复抛 `PLUGIN_DUPLICATE`；`value === undefined` 抛 `SERVICE_NOT_FOUND`；返回**幂等撤销函数**（仅当注册项仍是自己时才删除）。
- `get(id)`：缺失抛 `SERVICE_NOT_FOUND`；`optional(id)`：缺失返回 `undefined`；`has/list/removeOwner`。

**声明式访问控制**（三层闸门，全部在 `PluginContext` 内实现）：

1. `allowedRead = requires ∪ optional ∪ provides`；读取未声明服务 → `PLUGIN_PERMISSION_DENIED`（`Undeclared service: <id> -> <service>`）。
2. `register(service, …)` 时校验该服务在 `services.provides` 中，否则 `PLUGIN_PERMISSION_DENIED`（`Undeclared service export`）。
3. 所有 context 方法先过 `assertActive()`：signal 已 abort 则抛 `PLUGIN_INACTIVE`——保证**卸载后的插件无法再注册/读取/发事件**。
4. `list()` 被过滤为只返回 `allowedRead` 内的条目（防止探测他人服务）。
5. `declare → 校验`：激活完成后宿主反查 `services.provides` 每个名字是否确实由本插件注册，缺失即抛 `SERVICE_NOT_FOUND`，避免「声明了但没提供」的静默错误。

### 3.6 事件总线

`EventBus(onError)`：

- `on(name, listener)` 返回取消订阅函数；`emit(name, value)` 遍历快照副本，单个 listener 抛错**不影响主流程**，错误交给 `onError`（宿主注入 `logger.error('[plugins] Event listener failed')`）。
- 插件侧 `context.events.on` 的取消函数自动进入 dispose 队列。
- 宿主内建事件：`plugin.activated`、`plugin.failed`、`plugin.deactivated`。
- 浏览器侧另有跨模块 UI 事件字符串，例如 `nako:skill-catalog-changed`（`skillCatalog.js`）、`WORKFLOW_CANVAS_INSERTED_EVENT`、`WORKFLOW_LIBRARY_EVENT`（local-runtime api）。

### 3.7 路由贡献与装配阶段

`RouteContributions`（kernel/application.js）：

- `contribute(context, router, {phase=20, order=0})`：登记条目并 `context.onDispose` 自动摘除（激活回滚即撤销路由）。
- `mount(app, phase)`：按 `phase` 过滤后按 `order` **升序** `app.use`。挂载用一层间接（`app.use((req,res,next)=> entries.includes(entry) ? entry.router(req,res,next) : next())`），使运行期撤销立即生效。

### 3.9 凭据与密钥边界

四层闸门，缺一不可：

```text
plugins/providers/<x>/manifest.json  credentials: ['provider.x']
config/backend-plugins.json          credentialKeys / credentialGrants
        │
        ▼
createCredentialStore({ declarations, readSecret })      ← identity-account
        │  未知命名空间 → CREDENTIAL_SCOPE_DENIED
        ▼
PluginHost.options.credentialGrants[id]                  ← 宿主级授权
        │  manifest.credentials 未含 || grants 未含 → PLUGIN_PERMISSION_DENIED
        ▼
context.credentials.get('provider.x') → { getter(key) → readSecret(key) }
```

- `createCredentialStore` 返回的对象：未知命名空间直接抛 `CREDENTIAL_SCOPE_DENIED`；已知命名空间返回一个**每个键都是不可枚举 getter** 的冻结对象，调用时才 `readSecret(key)`（惰性、不做缓存）。
- `createServerPluginHost` 默认 `readSecret = key => process.env[key]`；桌面环境下由 `apps/desktop/src/backendEnvironment.mjs` 注入 DPAPI 解出的进程环境。
- `providerSecrets.js` 的 `USER_PROVIDER_SECRET_KEYS`（21 键）是「用户可配置密钥」的登记表，用于生成预算指纹与发布环境白名单。
- **红线**：Provider 插件每次调用都从 `context.credentials.get(manifest.id)` 重新取密钥，**绝不信任调用方传入的 provider 配置里的密钥**。

### 3.10 公开 API 边界（exports.json）

**`defineProviderPlugin` 详细行为（插件化的核心）**

1. 深拷贝 manifest；逐个 `validateProviderDescriptor` 后 `Object.freeze`；**manifest `providers[]` 必须与传入 descriptors JSON 严格相等**，否则 `PLUGIN_INVALID_MANIFEST`。
2. `activate(context)`：`await loadHandlers()` → `registry = context.services.get('generation.providers')` → 置 `active = true` 并 `onDispose(() => active = false)`。
3. 每个 descriptor 必须在 handlers 中存在同名导出，否则 `PLUGIN_INVALID_MANIFEST`。
4. **方法发布规则**：对 `descriptor.kinds` 每个 kind 取 `Suffix = kind 首字母大写 + 其余`（`image→Image`…）；`generate{Suffix}` 必须存在；`canRecover{Suffix}` 与 `recover{Suffix}` 必须**同时存在或同时缺失**。只发布这些方法，不复制实现内部字段或其他方法。
5. **上下文参数替换**：调用时把 `generate*` 的 `args[1]`、`canRecover*`/`recover*` 的 `args[2]` 替换为一个只读 `Proxy`，按以下**固定优先序**解析 key：
   1. 匹配 `/(?:API_KEY|ACCESS_KEY|SECRET_KEY|TOKEN|PASSWORD)$/` → `context.credentials.get(manifest.id)` 中的值（即**按插件自己的凭据命名空间**授予）。
   2. `REQUEST_CONTEXT` 集合（`LOGS_DIR`、`LIBRARY_DIR`、`LIBRARY_MEDIA_DIR`、`HTTPS_PROXY`、`signal`、`generationSignal`、`generationTaskSubmitting/Submitted/SubmissionRejected`、`NAKO_SINGLE_SUBMIT_ATTEMPT`）或 manifest `contextKeys` 中的 key → 调用方传入值。
   3. manifest `configPrefixes` 前缀命中的 key → `context.config.get(key)`。
   4. 其余 → `undefined`。**调用方配置不能作为密钥回退**。
6. **in-flight 计数**：`canRecover*` 为同步直通、不计入；`generate*`/`recover*` 包成 async，进入前 `inFlight++`、`finally` `inFlight--`；`canDeactivate()` 返回 `inFlight === 0`。
7. **禁用/再激活语义**：调用时 `!active || context.signal.aborted` → `PLUGIN_INACTIVE`；dispose 只置 `active = false`（不注销服务）；再次激活会重新 `loadHandlers` 并重新注册。
8. **发布**：`handler` 冻结后 `register('provider.<name>', wrapped)`，并把 descriptor（附 `pluginId`）注册进 `generation.providers`。

- 激活流程：
  1. `load()` 取实现模块；若给了 `loadClient`，用 `WORKFLOW_CLIENT_METHODS` 白名单包装客户端——只发布实现**确实拥有**的方法，且每次调用先检查 `context.signal.aborted`，否则 `PLUGIN_INACTIVE`。

  4. 发布执行器对象：`id`、`canExecute(definition) => definition?.runtimeKind === id`，再按 `WORKFLOW_EXECUTOR_METHODS` 逐个包装实现支持的方法（每次调用检查 abort、`activeExecutions++/--`）。返回 `Object.freeze`。
  5. 注册 `workflow.factory.<id>` 与 `workflow.executors.register(id, factory)`，两者都进 dispose 队列。
- **发布纪律**：只发布方法，**绝不暴露实现的 store / client / 凭据解析器**。

## 五、核心契约接口详细设计

第一部分给出的 6 个接口在实际契约中的**完整形状**（`modules/contracts/index.d.ts`）：

### 5.1 `NakoPlugin` / `PluginManifest` / `PluginContext`

```ts
interface NakoPlugin {
  manifest: PluginManifest;
  activate(context: PluginContext): Promise<void> | void;
  canDeactivate?(): boolean;          // 热卸载前自检
  deactivate?(): Promise<void> | void;
}
```

| context 成员 | 语义 |
| --- | --- |
| `pluginId` | 只读，等于 manifest.id |
| `signal: AbortSignal` | 卸载/激活失败时 abort；所有 context 方法先检查 |
| `services` | `register/get/optional/has/list`（**无 `removeOwner`**，卸载由宿主统一清理） |
| `events` | `on(name, listener): () => void`、`emit(name, value?)` |
| `config` | `get<T>(key, fallback?): T` |
| `credentials` | `get(providerId): unknown` |
| `logger` | `info/warn/error`（自动加 `[id]` 前缀与脱敏） |
| `onDispose(fn)` | 逆序执行；激活失败时也执行 |

> `PluginManifest` 字段见 3.4。除 `manifest` 本身外，宿主额外强制声明式 `services` 读写控制、`credentials` 授权与 `reloadRequired`/`canDeactivate` 热卸载语义；`deactivate` 为可选。

### 5.2 `ProjectRepository`（4 方法）

```ts
interface ProjectRepository {
  get(id: string): Promise<Project | null>;
  list(): Promise<Project[]>;                    // 新增
  save(project: Project): Promise<SaveResult>;   // SaveResult = { id, revision }
  delete(id: string): Promise<void>;
}
```

实现提供者：`plugins/storage/sqlite`（`project.repository`）。`Project.revision` 是并发控制的版本号载体。

### 5.3 `MediaStore` / `MediaProcessor`（+ 操作面扩展）

```ts
interface MediaStore { save(input: MediaInput): Promise<MediaAsset>; read(id: string): Promise<MediaAsset | null>; remove(id: string): Promise<void>; }
interface MediaProcessor { crop(input: CropInput): Promise<MediaAsset>; trimVideo(input: TrimInput): Promise<MediaAsset>; }
```

契约把「存储」与「处理」显式拆开，并以操作面契约补齐 Router 需要的批量能力：

- `MediaLibraryOperations`：11 个操作（`save/list/importAsset/update/remove/listWorkflows/saveWorkflow/importWorkflow/removeWorkflow/listPublicWorkflows/readPublicWorkflow`），统一签名 `(MediaOperationInput) => Promise<MediaOperationResult>`，输出 `{status, body}`。
- `MediaDownloadOperations`：6 个操作（`settings/updateSettings/selectDirectory/resetDirectory/save/openDirectory`），输入 `{scope: {libraryDirectory, configDirectory}, body?}`。

这样 Router 只做「参数校验 + 转发」，不触碰 fs。

### 5.4 `GenerationProvider` / `GenerationHandler` / `ProviderDescriptor`

契约把「声明」（descriptor）与「处理」（handler）分离：

```ts
interface ProviderDescriptor { name: string; kinds: GenerationKind[]; execution: 'immediate'|'polling'; requiredSecrets: string[]; pluginId?: string; }
interface GenerationHandler {
  id: string;
  capabilities(): ModelCapability[];
  generateImage?(...): Promise<GenerationResult>;
  generateVideo?(...): Promise<GenerationResult>;
  generateAudio?(...): Promise<GenerationResult>;
  generateText?(...): Promise<GenerationResult>;
  canRecoverImage?: RecoveryPredicate; recoverImage?: RecoveryHandler;   // 四类 kind 各自成对
  canRecoverVideo?; recoverVideo?; canRecoverAudio?; recoverAudio?; canRecoverText?; recoverText?;
}
interface GenerationProvider { descriptor: Readonly<ProviderDescriptor>; handler: Readonly<GenerationHandler>; }
```

映射规则：`kinds` 中的 `image/video/audio/text` → 首字母大写的 `Generate/Recover` 方法后缀；`execution: 'polling'` 对应异步任务（需 `canRecover*/recover*`），`'immediate'` 对应同步返回。

### 5.5 `WorkflowExecutor` / `WorkflowClient`

```ts
interface WorkflowExecutor {
  id: string;
  canExecute(definition: WorkflowDefinition): boolean;
  execute(request: WorkflowRunRequest): Promise<WorkflowRunResult | void>;
  resume?(request: WorkflowResumeRequest): Promise<WorkflowRunResult | void>;
  retryInputCleanup?(runId: string): Promise<unknown>;
  markRecoveryInputsOrphaned?(task: Record<string, unknown>, code: string): Promise<void>;
  markInputsOrphaned?(request: WorkflowInputCleanup): Promise<void>;
  cleanupInputs?(request: WorkflowInputCleanup): Promise<void>;
}
```

`WorkflowRunRequest = { runId, definitionId, deploymentId, bindingSetId, projectId, values, instanceType?, signal? }`；`canExecute` 的实际实现按 `definition.runtimeKind === id` 匹配。

客户端 12 白名单方法：`getSystemStats`、`getObjectInfo`、`supportsAtomicJobCancel`、`uploadInput`、`getWebAppInfoForProtocol`、`getWebAppInfo`、`getWorkflowApiFormat`、`getGlobalAiAppPageInfo`、`getWebAppCover`、`openOutput`、`validateCredential`、`resolveWebAppInfo`。

### 5.6 画布控制与 Agent 会话契约

- `CanvasControl`：以 `action` 为判别键的联合（`read/workflows/workflow/product/budgets/revokeBudget/prepareBudget/runGeneration/media/tasks/cancelTask/projects/models/prepareGeneration/edit/undo/focus/assets/importAsset` + `ProjectCommand`）；除 `{action:'read'}` 外多数带 `revision` 做乐观并发；`CanvasEdit` 11 种编辑操作。
- `CanvasResult`：`{ok:false, code}` 或 `{ok:true, revision, operationId?, …}`；`afterTurn?: () => Promise<void>` 是**仅本地延续**字段，**永不序列化给模型或后端**。
- `AgentEvent`：`{protocol: 2, type, sessionId, runId, sequence, payload}`。
- `AgentSessionRepository`：`get/commit(record, expectedRevision)/list(projectId?)/remove(id)`——**commit 带期望版本**，是会话层的乐观并发契约。

## 六、关键流程详细设计

### 6.1 后端启动与插件激活（含失败回滚）

```text
apps/backend/main.mjs
 ├─ 解析 RUNTIME_PATHS（library/private/logs/dist/public/integrations）
 ├─ createServerPluginHost({ libraryDirectory, privateDirectory, runtime, routes })
 │   ├─ 读 plugins.json + backend-plugins.json
 │   ├─ createCredentialStore(declarations) / credentialGrants
 │   ├─ register：25 条后端插件（工厂条目经 options→路径名映射）
 │   ├─ register host.runtime（platform 类型，提供 host.runtime + http.routes）
 │   ├─ register：8 条 application 插件
 │   ├─ 禁用一致性校验 → host.start(selected)
 │   └─ 失败：逆拓扑 #stopExcept 卸载已激活者，错误上抛
 ├─ 认证边界 createExactLocalBoundary
 ├─ /healthz、/readyz、/api/plugins
 ├─ routes.mount(10) → express.json(200mb) → routes.mount(20) → routes.mount(30)
 └─ createLocalRuntimeLifecycle → launchRuntime（listen → ready）
```

**部分失败语义**：`start()` 不忽略错误；已激活插件按「无活动依赖者的叶子优先」逆序卸载，保证不会留下半初始化的依赖链。

### 6.2 插件激活上下文构建（每次激活的顺序）

```text
1. 递归加载 dependencies（环检测 chain + 版本范围 satisfiesVersion）
2. state = activating；new AbortController；dispose 队列清空
3. allowedRead = requires ∪ optional ∪ provides
4. 构造冻结 context（所有方法先 assertActive）
5. 预检：requires 中每个服务必须已在注册表中（services.get 抛错即失败）
6. await plugin.activate(context)
7. 反查：provides 中每个服务必须由本插件注册
8. state = active；emit('plugin.activated')
   任一步失败 → #cleanup（abort → 逆序 dispose → removeOwner）→ state=failed → emit('plugin.failed') → 重新抛
```

## 七、校验与红线详细设计

### 7.1 `check-architecture.mjs` 全部规则（第一部分的「关键规则」逐条机器化）

**A. 公共 API（exports.json）**

1. `exports.json` 中每个路径必须存在且以 `modules/<name>/api/` 开头（`invalid public API`）。
2. `modules/<name>/api/` 下每个文件必须被列出（`unlisted public API`）。

**B. 退休目录**

3. 顶层 `src/` 或 `server/` 目录存在即失败。
4. 任何字符串字面量以 `src/` 或 `server/` 开头即失败（`retired source path`）。

**C. 依赖方向（对应第一部分「关键规则」）**

5. `@earendil-works/pi-*` 只允许出现在 `modules/agent/`（`pi is private to agent`）。
6. `modules/agent/**` 不得 import `fs`/`node:fs`（Harness 持久化必须走存储适配器）。
7. `modules/asset-media/**/*Router.*` 不得 import `fs|path|child_process`。
8. `modules/contracts/**` 与 `modules/kernel/**` 不得有非相对 import（`package/platform dependency`）。
9. 相对 import 必须可解析到文件（`unresolved import`）。
10. `modules/**` 不得 import `plugins/**`（唯一豁免 `generation-core/models/catalog.ts`）。
11. `contracts` 的 import 目标必须仍在 `contracts` 内（`contracts depend on implementation`）。
12. `kernel` 的 import 目标只能是 `kernel|contracts`（`kernel depends on implementation`）。
13. `modules/**` 不得 import `apps/**`（`module imports application host`）。
14. 跨模块必须命中公共边界（见 3.1），否则 `crosses private module boundary`。
15. `plugins/**` 之间只允许同 owner 或 `/shared/` 路径（`imports another adapter implementation`）。
16. `/ui/` 下的文件不得 import `/server/` 或 `/desktop/`（`/ui/desktop/` 除外）。

**D. 反模式字符串**

17. 禁止 `window/target/targetWindow/globalThis.__NAKO_*` 形式的服务定位器。
18. 非 `scripts/`、非 `tests/` 文件禁止 `app.locals`/`request.app.locals`/`req.app.locals`。

**E. 5 个插件清单**

19. 清单内 id 重复即失败。
20. `entry` 无法解析即失败（浏览器清单以 `apps/canvas/main.tsx` 为基准，其余以清单文件为基准）。
21. `manifest` 无法解析即失败。
22. manifest 的 `id` 与清单条目 `id` 不一致即 `identity mismatch`。

全部失败一次性打印，`process.exitCode = 1`；通过时打印 `Architecture passed: <n> source files; no retired directories; public module APIs; 5 plugin catalogs.`

### 7.2 `check-local-only.mjs`（本地化红线）

扫描 `apps, modules, plugins, config, scripts, public, integrations` 下的 `.js/.ts/.tsx/.mjs/.cjs/.json/.html/.md`。

**禁止的正则**：官方域名/镜像链接；`provider.relay`/`account.relay`/`telemetry.calls`/`desktop.updates`/`Relay*Provider`；`account:submit-feedback`/`desktop:open-admin`/`identity:sign-in|register|sign-out`/`update:check|install`；`/v1/(call-telemetry|device-sessions|token-exchanges|authorization-codes)` 与 `/api/(auth/|account/relay)`；`telemetryReporter`/`modelCallReporter`/`__NAKO_BEFORE_DESKTOP_UPDATE__`/`inviteCode=rh-v1270`。

**禁止存在的路径**：`plugins/providers/relay`、`config/identity-runtime.json`、`modules/identity-account/ui/account`、`modules/identity-account/server/account`、`modules/desktop-shell-observability/ui/feedback`、`ui/updates`、`desktop/updates`。

**白名单断言**：`config/desktop-plugins.json` 的插件 id 必须 `deepEqual(['desktop.identity-account'])`。

### 7.3 第一部分「关键规则」的实现落点对照

| 第一部分规则 | 实现 / 校验 | 状态 |
| --- | --- | --- |
| `desktop-shell → kernel → contracts` | `apps/desktop` 与 `desktop-shell-observability` 依赖 kernel；kernel 只依赖 contracts（规则 8/11/12 强制） | ✅ |

### 7.4 与第一部分的对应关系

第一部分已按当前项目结构校准，因此本文档内部不存在「设计 vs 实现」的形状差异。阅读时需注意三处**结构性特例**：

## 八、错误码与日志规范

### 8.1 错误码（`contracts` 的 `ERRORS`，14 个）

| 码 | 触发点 |
| --- | --- |
| `PLUGIN_INVALID_MANIFEST` | manifest/descriptor 校验失败、生命周期方法类型错误、实现 manifest 与清单不一致、Provider 方法发布不合法、执行器缺 `execute` |
| `PLUGIN_API_INCOMPATIBLE` | `satisfiesVersion(PLUGIN_API_VERSION, manifest.apiVersion)` 为假 |
| `PLUGIN_DUPLICATE` | 插件 id 重复、服务 id 重复、workflow 客户端/执行器 id 重复 |
| `PLUGIN_NOT_FOUND` | 加载/卸载不存在的插件 |
| `PLUGIN_DEPENDENCY` | 依赖缺失/版本不满足/成环、有活动依赖者时卸载、无法排序关机 |
| `SERVICE_NOT_FOUND` | `services.get` 未注册、注册 `undefined`、声明的 provides 未实际提供 |
| `SERVICE_DUPLICATE` | `ServiceRegistry.register` id 冲突 |
| `PLUGIN_PERMISSION_DENIED` | 读取/导出未声明服务、读取未授权凭据命名空间 |
| `PLUGIN_BUSY` | `reloadRequired` 或 `canDeactivate() === false` 时热卸载 |
| `PLUGIN_INACTIVE` | 已禁用/已卸载插件被调用；执行器与客户端在 abort 后调用 |
| `INVALID_MEDIA_ASSET` | 媒体资源非法 |
| `INVALID_PROJECT_ARCHIVE` | 项目归档非法 |
| `PROJECT_TRANSFER_FAILED` | 项目导入导出失败 |
| `AGENT_OPERATION_SYNC_FAILED` | Agent 操作回执同步失败 |

另有两个**契约外**错误族：`CREDENTIAL_SCOPE_DENIED`（凭据命名空间越界，`credentialStore` 抛出）与 `workflowProtocols.js` 的 4 个错误类（`LocalComfyClientError`/`LocalComfyExecutorError`/`RunningHubWorkflowExecutorError`/`RunningHubWorkflowClientError`，均带 `code/status`，执行器族另带 `retryable`）。

### 8.2 日志规范

- 一律经 `context.logger.{info,warn,error}`，自动加 `[<pluginId>]` 前缀，并正则脱敏 `Bearer …` 与 `sk-…`。
- 宿主内部：事件监听器失败 → `logger.error('[plugins] Event listener failed')`；资源清理失败 → `logger.error('[plugins] Resource cleanup failed')`；**不打印插件载荷、请求体与凭据**。
- 禁止裸 `console.log`；服务端安全日志经 `requestContext` 的 `createSecureLogger` / `installSecureConsole`，脱敏函数为 `redactSensitive` / `redactSecretsOnly`。

## 十、扩展实施清单（详细设计）

### 10.1 新增 Provider 插件

1. 建 `plugins/providers/<name>/`：`manifest.json`、`index.js`、`implementation.js`、`models.ts`。
2. `manifest.json`：`type: "provider"`；`capabilities`（如 `generation.image`）；`services.requires: ["generation.providers"]`；`services.provides: ["provider.<Xxx>Provider"]`；`credentials: ["provider.<name>"]`；`providers: [{ name, kinds, execution, requiredSecrets }]`（`name` 必须 ≥2 字符、字母数字）。
3. `index.js`：`export default defineProviderPlugin(manifest, manifest.providers, () => import('./implementation.js'))`。
4. `implementation.js`：导出与 `providers[].name` **同名**的 handler，实现对应 `generate{Suffix}`；polling 类型必须成对实现 `canRecover{Suffix}`/`recover{Suffix}`。
5. 在 `config/backend-plugins.json` 登记 `id`/`entry`/`manifest`/`credentialKeys`/`credentialGrants`（需要读 `RUNNINGHUB_*` 之类环境变量时再加 `configPrefixes`）。
6. 模型写 `models.ts`（导出 `TEXT_MODELS/IMAGE_MODELS/VIDEO_MODELS/AUDIO_MODELS`），在 `config/model-plugins.json` 声明 exports，然后 `npm run build:model-catalog`。
7. 新增密钥需同步 `modules/contracts/providerSecrets.js` 与 `scripts/release/runtimeControl.mjs` 的进程环境允许名单；来源设置与 Agent 兼容名单**独立显式登记**。

参考：`plugins/providers/openai/`、`plugins/providers/ecloud/`。

### 10.2 新增工作流执行器

1. 建 `plugins/workflows/<id>/`：`manifest.json`、`index.js`、`implementation.js`、可选 `client.js`。
2. `index.js` 用 `defineExecutorPlugin({ id, load, loadClient, exportName, credentialId })`。
3. `implementation.js` 实现 `canExecute`（按 `definition.runtimeKind === id`）、`execute`、`resume` 等；`client.js` 实现 12 白名单中的子集。
4. 在 `config/backend-plugins.json` 登记；需要 RunningHub 凭据时加 `credentialGrants: ["provider.runninghub"]`。
5. 错误类与输入校验一律用 `contracts/workflowProtocols.js`。

参考：`plugins/workflows/{local-comfyui,runninghub-workflow,runninghub-webapp}/`。

### 10.3 新增存储 / 媒体 / 平台适配器

1. 建目录 + `manifest.json` + `index.js` 工厂（如 `createXxxPlugin(options)`）。
2. 工厂返回 `{ manifest, activate }`；在 `activate` 内 `context.services.register('服务ID', 有限对象)` 并用 `context.onDispose()` 释放。
3. 在 `config/backend-plugins.json` 登记 `factory` 与 `options`（值用宿主路径名 `libraryDirectory`/`privateDirectory`/`generationDirectory`/`publicDirectory`）。
4. **只暴露有限方法**，不要把数据库句柄、密钥或原始客户端对象作为不受限公共服务返回。

参考：`plugins/storage/sqlite/`、`plugins/media/filesystem/`、`plugins/platform/text-transport/`。

### 10.4 新增后端业务模块

1. 建 `modules/<module>/serverPlugin.js`，用 `defineApplicationPlugin({ id, provides, activate })`。
2. `activate` 内创建 `express.Router()`，经 `context.services.get('http.routes').contribute(context, router, { phase, order })` 贡献（默认 20/0）；**不能在模块导入时启动进程或注册路由**。
3. 在 `config/application-plugins.json` 登记 entry + `server.manifest.json`（`id` 必须与 `defineApplicationPlugin` 的 id 一致）。
4. 依赖数据一律经 `context.services.get(...)`，需要声明在 manifest 的 `services.requires`。

参考：`modules/identity-account/serverPlugin.js`。

### 10.5 新增浏览器 UI 模块

1. 建 `browser.ts`（或 `rootPlugin.tsx`），用 `activateBrowserModule(context, activate)` 装配，用 `trackBrowserResource` 登记带 `destroy/dispose` 的对象。
2. 在 `config/browser-plugins.json` 登记 entry + `browser.manifest.json`（相对 `apps/canvas`）。
3. 跨模块 UI 能力经宿主服务装配（如 `ui.agent.surfaces`）；根视图由 `ui.canvas-shell` 提供 `ui.root`。

### 10.6 新增桌面插件

1. 建 `modules/<module>/desktopPlugin.mjs` + `desktop.manifest.json`。
2. `activate` 内经 `context.services.get('desktop.environment')` 取平台环境，注册桌面服务。
3. 在 `config/desktop-plugins.json` 登记——**注意**：`check-local-only.mjs` 断言该清单必须恰为 `['desktop.identity-account']`，新增条目会直接失败，需同步修改红线断言。
4. 窗口与 IPC 留在宿主，不在插件内重复实现。

参考：`modules/identity-account/desktopPlugin.mjs`。
